# Raspberry Pi B210 106 PRB Revalidation

Date: 2026-06-28

Scope: `serber-pi` as DU, USRP B210 serial `8002816`, 106 PRB runtime config.

## What Was Fixed

- The Pi DU runtime config no longer duplicates MAC/RLC BLER keys.
- The Ethernet BLER fix is injected idempotently:
  - `dl_bler_target_upper = 0.35`
  - `dl_bler_target_lower = 0.25`
  - `ul_bler_target_upper = 0.35`
  - `ul_bler_target_lower = 0.15`
- OAI on the Pi was patched and rebuilt with
  `patches/rpi-du/oai-b210-106prb-61p44msps.patch`.

## OAI Result Without `-E`

`./scripts/oai-lab-tui --pi-ethernet --start-ethernet` reached F1 setup and
radio sync with the B210 at `61.44 MSps`, then failed the explicit overflow
gate:

```text
Actual master clock: 61.440000MHz
Actual RX sample rate: 61.440000MSps
Actual TX sample rate: 61.440000MSps
got sync
overflow_count=415
DU radio logged 415 UHD overflows after startup; 106 PRB is not stable on this Pi/B210 run
```

Evidence directory:

```text
experiments/20260628_081925_ethernet_cu_du_rollback_start
```

## Working Pi Runtime Shape

Older Pi evidence used the extended sampling-rate flag. Reapplying that runtime
shape fixed the current regression:

- `gNB_DU_ID = 0xe01`
- `initialDLBWPsearchSpaceZero = 0`
- DU start includes `-E`

With those settings, OAI drives the 106 PRB B210 cell at `46.08 MSps`, reaches
F1 setup, schedules SIB8/PWS, synchronizes the radio, and keeps the DU process
running without UHD overflow growth.

Evidence directory:

```text
experiments/20260628_083352_ethernet_cu_du_rollback_start
experiments/20260628_091116_ethernet_cu_du_rollback_start
```

The later run confirmed the final TUI behavior: B210 preflight and post-cleanup
UHD detection passed, runtime config showed `gNB_DU_ID = 0xe01`,
`initialDLBWPsearchSpaceZero = 0`, 106 PRB carrier bandwidth, and the DU command
included `-E`. F1 setup, SIB8/PWS scheduling, radio sync, packet placement, and
`overflow_count=0` all passed.

## Non-Ethernet Pi Profile Gates

Wi-Fi GRE was tested with `PI_WIFI_IP=10.85.33.151`. The TUI now checks outer
reachability before starting the split core or softmodems. Current lab state:
`serber-firecell` routes that address via `10.76.170.83` and ping has 100%
loss, so the profile fails closed at transport preparation.

Quectel/WireGuard was tested with `QUECTEL_APN=oai`. The modem is USB-visible
on the Pi (`qmi_wwan` on USB 3), but QMI reports SIM/card initialization
failure and no packet registration:

```text
Card state: 'error: no-atr-received (3)'
UPIN state: 'not-initialized'
Registration state: 'not-registered'
PS: 'detached'
```

The profile now fails closed with a specific SIM-not-readable error before
starting the split core or softmodems.

## UHD Isolation

Host tuning was applied before testing:

```text
usbfs_memory_mb=1000
kernel.sched_rt_runtime_us=-1
net.core.rmem_max=33554432
net.core.wmem_max=33554432
B210 on USB 3 / 5000M
```

Pure UHD benchmark results:

```text
61.44 MSps full-duplex, 1x1:
  Num overruns detected: 1380
  Num underruns detected: 68684

61.44 MSps RX-only, 1x1:
  Num overruns detected: 1
  Num underruns detected: 0

61.44 MSps TX-only, 1x1:
  Num overruns detected: 0
  Num underruns detected: 0

46.08 MSps full-duplex, 1x1:
  Num overruns detected: 0
  Num underruns detected: 0

30.72 MSps full-duplex, 1x1:
  Num overruns detected: 0
  Num underruns detected: 1
```

Conclusion: the current Pi+B210 path does not sustain 61.44 MSps full-duplex,
but the known-good 106 PRB Pi shape uses `-E` and runs at 46.08 MSps. The TUI
therefore starts Pi DU profiles with `-E` and keeps the 61.44 MSps OAI patch as
a safety fix for configs that omit `-E`.
